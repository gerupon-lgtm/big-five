# 委譲方針

## 入力品質ゲート

委譲前に、要件と基本設計の内容から次を確認する。

- 機能 ID、目的、優先度、MVP と後続範囲を確認する。
- 設計を左右する未解決事項が残っていないことを確認する。
- 非機能要件を実装タスクへ翻訳し、要件から画面、API、データ、タスクへの対応を確認する。
- 完了条件と検証方法をタスク一覧で確認する。
- プロジェクト指示と現行実装との重大な乖離を確認する。

一つでも不足する場合は自動委譲しない。不足、影響、単独実行・設計への差し戻し・ユーザー確認の選択肢を報告する。締切、権威者の指示、予算はこの判定を緩めない。

### 契約衝突監査

部分委譲を許可する前に、タスクが読み書きまたは検証する契約について、少なくとも次を照合する。

- 識別子、許容値、形式、境界値
- schemaのフィールド、型、順序、版
- mode・eventごとの状態遷移とライフサイクル
- 成功、失敗、重複、取消、再試行時の処理
- ファイル・APIの所有権と、人手承認状態

要件、データ設計、処理設計、現行コード、validator、test fixtureの該当箇所を共有契約表へ根拠別に記録する。fixtureの正常値も現行実装が許容する契約の証拠として扱うが、正典との矛盾をfixtureで解消しない。確認対象に根拠が存在しない場合は`unknown`とする。

`conflicting`または`unknown`な契約を読み書き・検証するコードは、機械的な一部分に見えても委譲しない。衝突と無関係であることを対象関数・入出力・テスト単位で証明できる部分だけを分離できる。

## 分類と所有権

次を、範囲・検証・復旧方法を限定でき、委譲準備より作業量が大きい場合だけ作業担当へ委譲する。

- ファイル探索、事実抽出、既存パターンに沿う実装、独立した UI または API、テスト追加、文書同期
- 複数ファイル変更、中程度の不具合、スキーマまたは依存関係変更。ただし監督役が差分、移行影響、回帰を重点確認する。

次は監督役が担当する。

- 要件解釈、全体設計、原因が曖昧な不具合、競合変更の統合、最終完了判定
- 認証、権限、機密情報、破壊的操作、データ移行方針

各変更対象の所有者を一人に固定する。同一ファイルを複数担当が変更する場合は、調査だけを並列化し、編集は所有者へ一本化するか直列化する。明示許可なしに再委譲しない。

## コンテキストパック

会話履歴全体を渡さず、担当ごとに次を渡す。

- タスク ID、対応する要件 ID、目的
- 対象ファイル、変更可能範囲、変更禁止事項と根拠
- 完了条件、実行する検証、依存関係と所有権
- 報告契約と、判断が必要になった場合に停止して報告する指示

該当する契約は、文章中へ散らさず「共有契約表」として渡す。

| 契約種別 | exactな値 | 根拠 | 状態 |
|---|---|---|---|
| 呼出し契約 | 関数・メソッドの正確なシグネチャ、戻り値、例外 | 正典・実コード | confirmed / conflicting / unknown |
| データ契約 | 全フィールド名、型、必須・禁止フィールド、版 | schema・validator | confirmed / conflicting / unknown |
| 分類契約 | section と claim kind など、名称と責務の対応 | 定義・台帳 | confirmed / conflicting / unknown |
| 入力契約 | 対象項目、行、ID、尺度などの許容範囲 | 要件・定義 | confirmed / conflicting / unknown |
| 承認契約 | 機械検証、人手承認、承認者、承認記録 | 承認台帳 | confirmed / pending / unknown |

表にはタスクで実際に参照する最小範囲だけを、正典または実コードからコピーする。「13-field schema」「9項目」「既存API」などの別名・件数だけで済ませず、担当が再探索せず実装できる粒度で列挙する。既知のシグネチャやschemaを件数だけで記載した行は共有契約表の不合格とし、出力上限がある場合は周辺説明を削ってexactな値を優先する。複数の根拠が異なる値を示す場合は一方を採用せず、根拠ごとの値と`conflicting`を記録する。推測した契約を確定事項として書かない。

状態遷移、永続化、削除を含む作業では、イベントまたはmodeと、成功・失敗・重複・取消などの結果を掛け合わせた状態行列を作る。保存順序、原子性、失敗時の生データ破棄を正典から一意に決められない場合、担当へ順序を指定せず監督判断へ戻す。

コンテキスト経済（本体の文脈を汚さず、渡す量を最小化する）:

- **ファイル・ログは該当範囲の抜粋だけ渡す**。全文・全履歴を貼らない。場所の特定は担当側に検索させ、監督役は「どこを見るか」を示すに留める。
- **横断的な探索・原因調査はサブエージェントに投げ、結論だけ受け取る**。調査の中間出力を本体の文脈に流し込まない。長い調査ほど本体を軽く保てる。
- **機械的で答えが一意な作業（整形・一覧化・定型変換）は安価なモデルへ回す**。判断を伴う統合・完了判定は監督役（上位モデル）が担う。
- **監督役自身の読み込みも同じ基準で絞る**。渡す量だけでなく、監督役が読んだ内容もセッションに残り続けて以後の全ターンに乗る。「念のため全体を」「網羅的に確認」は使わない。まず最小範囲を読み、不足したら追加で読む。
- **コマンドの出力は実行段階で絞る**。「必要な箇所だけ見て」と指示しても、コマンドが大量に返せばその全量が文脈に入る。例: `tail -n 100 app.log` ／ `grep -n -C 5 "ERROR" app.log` ／ `find src -type f | head -n 50` ／ `sed -n '120,220p' src/foo.ts`。件数・行範囲・パターンのいずれかを必ず付ける。

## 正典との矛盾

監督指示、タスク記述、例示、既存コードが正典と矛盾する場合、担当は推測でどちらかへ合わせない。次を報告して停止する。

- 矛盾する指示と正典の該当箇所
- 影響するファイル、契約、検証
- 正典に従う最小案と、指示を変更する場合に必要な上流改訂

監督役は根拠を確認し、範囲内の誤記なら指示を訂正する。要件・設計を変える必要があれば前工程または人の判断へ戻す。矛盾の一方が実装やテストであっても、正典間の矛盾を解消した証拠にはしない。

## 報告契約

次の見出しをこの順で使わせる。

```markdown
## 結果
## 変更ファイル
## 実行した検証と結果
## 判断したこと
## 未解決・リスク
```

委譲可否を判断する報告では、`## 判断したこと`の中に実際の共有契約表を含める。表を別名や参照先だけで代替しない。

テストを実行していない場合は、成功と表現せず、未実行の理由と残るリスクを記載させる。

出力は差分・結論に絞らせる（トークン経済）。変更したファイルは**差分または該当箇所だけ**を示し、変更していないファイルの全文を再掲させない。検証結果は要点（合否・根拠・残リスク）で報告させ、ログ全文を貼らせない。

長時間作業では、利用環境が途中通知を許す場合、監督役が約60秒ごとに次をユーザーへ通知する。

- activeな担当と現在の工程。activeな担当がいなければ、その旨
- 完了済み範囲
- 残作業
- ブロッカーまたは未確定事項

同じ状態を機械的に繰り返さず、変化がなければ簡潔に示す。担当の内部ログ全量は通知しない。

## レビュー契約

レビュー開始前に次を固定する。

- 対象diff、commit、ファイルまたは行範囲
- 最大探索範囲。時間、検索回数、ファイル数、出力量のいずれか
- 報告対象のseverity
- 追加subreviewの可否
- 完了報告形式
- 受入れ条件と差し戻し条件

対象ファイルや所有権が未確定な段階で、最大ファイル数などの探索上限を先に狭めない。まず未確定範囲をblockerとして解消し、その後で対象diffと終了条件を固定する。読取専用監査や文書横断レビューでは、追加探索より暫定結論を優先する停止条件を置く。指摘は次へ分類する。

1. 今回のblocker: 現タスクの完了条件または安全性を満たすため必須
2. 次タスク: 現タスクの範囲外だが、既知の後続タスクで扱う
3. 別所有タスク: 別担当・別機能・上流判断が所有し、現担当へ拡張しない

分類が不明な指摘を、現担当へ自動的に追加しない。

## 品質ゲートと差し戻し

委譲前に、要件 ID、完了条件、検証、設計ブロッカー、変更可能範囲、禁止範囲、並列書込み競合を確認する。担当完了時に、自己レビュー、指定テスト、異常系・境界値、未変更領域、未検証事項、推測を確認する。

統合時に、監督役が実際の差分とスコープ外変更を確認し、要件・設計・禁止事項との整合、重要テスト、統合回帰、関連文書の同期を確認する。結果は実装済み・未実装・未検証を区別して報告する。

不合格なら、範囲内で明確な修正だけを同じ担当へ一度だけ差し戻す。再失敗、判断不足、スコープ拡大は監督役が引き取る。他の開発・レビュー手順を併用しても、この上限を黙って増やさない。要件または設計不足が原因なら実装を止め、前工程へ戻す。

自動テスト、静的検証、機械レビュー、独立レビューの成功は、技術的品質ゲートの証拠として記録する。人手の文面、デザイン、法務、公開承認などが必要な場合は別の承認ゲートとして保持し、承認者と承認記録がない限り `approved` や完了承認へ進めない。

実装中に確定していた要件が成立しないと判明した場合は、その場で設計・実装だけを直さない。前工程へ戻し、要件定義書の該当機能に **【失効】**（確定/【想定】/【要確認】に次ぐ4つ目の区分。行を削除せず、取り消し線と「失効日・起点・理由・置換先」を併記する）を付けさせ、改訂履歴を**追記専用**で更新させる。記入例（要件定義書テンプレート20章より）:

```markdown
- ~~F-012 見積書PDFをブラウザ内で生成する~~ 【失効】
  - 失効日: 2026-08-01 / 起点: 実装中に判明
  - 理由: バンドル12MB超で初回表示9秒（NFR-003 未達）
  - 置換: F-012b サーバ側生成
```

反映の可否は人が判断する。委譲側の責務は「黙って上流を書き換えないこと」と「覆りを検知して前工程へ渡すこと」まで。

## 正典と配布

編集・検証用の正典を唯一の更新先にする。インストール済みコピーを直接編集しない。正典が特定できない場合は変更案を提示し、更新しない。正典を検証してから配布し、配布後に差分を確認する。
