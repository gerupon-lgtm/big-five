# delegate-development 利用者向け日本語文案の品質不合格と修正指示

## 結果

`titleReflection`のTR-0（11称号×3件）を、共有資料、表現境界、既存文との
重複禁止、役割分離を含むtask briefで委譲した。構造検査、禁止語lint、
独立レビュー、1回の差し戻しは通過可能な状態まで進んだが、プロジェクト
オーナーの品質判定では、全体に人間が通常使わない言い回しが多く、
「すべての質が低い」として不合格になった。

本件はアプリのロジック不具合ではない。機械検査と契約レビューだけでは、
日本語としての自然さ、生活場面の想起しやすさ、既存の承認済みトーンを
保証できなかった委譲品質の問題である。

## 発生条件

- 対象: 利用者が結果画面で直接読む日本語の問いかけ・行動ヒント
- 作業量: 11称号、33候補
- 入力: 統合候補資料、承認済み設計、既存237文、構造化task brief
- 担当: 文案作成担当1名、独立レビュー担当1名
- 機械検査: ID、順序、件数、status、禁止語、完全重複、空白を通過
- 人手判定: 全体品質不合格

## 検出できなかった問題

- 「最後に残したい条件」「何のために大切にしたい」など、意味は解釈できても
  日常の日本語として選ばれにくい抽象表現。
- 元資料の意味を薄く抽象化し、利用者が具体的な場面を思い浮かべにくくした文。
- `何を手がかりにしますか`、`時間を置く`など、文法上は成立しても会話では
  不自然な語の組み合わせ。
- 禁止断定を避けることを優先しすぎ、既存の承認済み文面にあった自然な具体性、
  引用表現、感情の動きまで失った文。

## 修正指示

1. 利用者向けの文案作成は、高リスクな人手品質タスクとして監督役が本文を
   所有する。担当へ委譲する場合も、初回は3称号以下のsample gateに限定し、
   project ownerのトーン承認前に11件以上へ展開しない。
2. task briefには禁止事項だけでなく、project ownerが承認した日本語文を
   5件以上そのまま載せる。各例について「具体的な生活場面」「自然な引用」
   「読点数」「問いの長さ」をacceptance patternとして示す。
3. `自然な日本語`を抽象的な受入条件で終わらせない。次をレビュー項目へ追加する。
   - 日常会話や一般向けWebサービスで実際に使われる語の組み合わせか。
   - 一読して具体的な場面を思い浮かべられるか。
   - 抽象名詞を二つ以上重ねていないか。
   - 元資料の具体性を理由なく削っていないか。
   - 声に出して読んだときに修飾関係が迷わないか。
4. copy lintと既存文重複検査は必要条件として維持するが、合格を人手品質の
   代替にしない。独立レビュー報告には契約適合と日本語品質を別見出しで記録する。
5. 文案担当の1回目が全体的なトーン不合格になった場合、同担当への局所修正で
   継続しない。監督役が元資料へ戻って全件を再構成し、旧案を部分流用しない。

## 暫定対応

- TR-0の旧33候補は承認せず`draft`を維持する。
- project ownerが指定した確定置換だけを保持する。
- 監督役が添付資料の該当11節から全33件を最初から再構成する。
- 再構成後は新しい読取専用レビューを実施し、project ownerへ再提示する。
- CSV、runtime、承認メタデータ、commit、pushへは進めない。

## 判断

配布済みskillは直接変更しない。本書をdelegate-developmentの改善候補として
残し、本プロジェクトでは文案本文を監督役所有へ切り替える。
