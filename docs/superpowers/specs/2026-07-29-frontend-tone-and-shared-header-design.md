# フロントエンドトーン・共通ヘッダー再設計

- 状態: ユーザー承認済み
- 対象版: `mvp-0.1.0`
- 対象機能: F-001、F-003〜F-010、F-013、F-015
- 対象画面: S-001〜S-004、S-006、S-007
- 対応タスク: T-008Aの後続UI調整
- 承認日: 2026-07-29

## 1. 目的

開始、回答、結果、履歴、比較の各画面に同じアプリらしさを持たせ、スマートフォンで見たときの情報階層と操作の意味を明確にする。

運用中の「AIリテラシー検定」は、次の点に限って参照する。

- 小さな共通ヘッダーでアプリ名を継続表示する
- 英字の補助見出し、主見出し、説明、カード、操作の順に情報を整理する
- 主操作と補助操作を近接させすぎない
- 見出しを過度に大きくせず、本文を読み進めやすくする

ブランド、配色、アイコン、文面を複製するものではない。Big Fiveアプリの淡い緑、白いカード、猫の表現は維持する。

## 2. 非対象

本変更では次を変えない。

- IPIP日本語50項目版の設問、順序、採点、判定、称号選択
- 承認済みの称号、副題、称号理由、因子別結果文
- 20問完答後の分岐、途中保存、履歴、比較、削除の状態遷移
- ResultSnapshot、ProgressRecord、localStorageの保存形式
- 結果画面の情報優先順位と段階的な開閉構造
- キャラクター、色、香り、共有のドメイン契約

画面のトーン、共通部品、配置、余白、文字階層、利用者向けラベルだけを再整理する。

## 3. 表示名称と固定文言

### 3.1 共通表示

- アプリ名: `Big Five 自己理解チェック`
- 英字副題: `BIG FIVE SELF UNDERSTANDING`
- フォント:

```css
--font-sans: "Sawarabi Gothic", "Hiragino Kaku Gothic ProN",
  "Yu Gothic", "Meiryo", system-ui, sans-serif;
```

外部フォントの実行時取得は追加しない。端末にSawarabi Gothicがあれば優先し、なければ既存の日本語システムフォントへ安全にフォールバックする。

### 3.2 開始画面

- 英字見出し: `SELF CHECK`
- 主見出し: `自分のことを知る`
- 説明:

> Big Fiveは、性格傾向を5つの因子から捉える考え方です。本チェックではIPIP日本語50項目版を使用し、回答から現在の傾向を振り返ります。

`5つの傾向`、右上の`はじめる`、`正式版MVPを準備中です`は開始画面から外す。尺度版、設問版、採点版などの診断版情報は削除せず、画面下部の簡潔な`この診断について`から確認できるようにする。

## 4. 共通ビジュアル

### 4.1 色と面

- 背景は現在の淡い緑から白へ緩やかにつながる面を維持する
- 主要カードは白またはごく薄い白緑とし、境界線と弱い影で背景から分ける
- 主操作は現在の濃い緑を維持する
- 英字見出し、進捗、補助ラベルは同じ緑の文字色を使う
- 本文は濃い緑黒とし、純黒を多用しない
- 危険操作は主操作の緑と混同せず、削除であることを文言と色の両方で示す

### 4.2 文字階層

基準値は次のとおりとし、320pxで破綻しない範囲だけ調整する。

| 役割 | モバイル基準 | 行間 | 備考 |
|---|---:|---:|---|
| ヘッダーのアプリ名 | 12px | 1.35 | 太字。1行を優先 |
| ヘッダーの英字副題 | 8px | 1.2 | 字間を広げる |
| ヘッダー操作 | 12px | 1.35 | `white-space: nowrap` |
| 画面の英字見出し・進捗 | 12px | 1.4 | 緑、字間を広げる |
| 開始・履歴・比較の主見出し | 22〜24px | 1.4 | 過度な`clamp()`拡大をしない |
| 回答の設問 | 20〜22px | 1.5 | 既存の承認済み回答画面基準を維持 |
| 結果の主見出し | 22〜24px | 1.4 | 結果本文より先に読める範囲 |
| 本文 | 16px | 1.75 | 日本語の読みやすさを優先 |
| ボタン・回答選択肢 | 16px | 1.5 | 回答選択肢の最小高さ56pxを維持 |
| 注記・版情報 | 12〜14px | 1.6 | 本文との階層差を明確にする |

200%拡大時も文字を切らない。ヘッダー名や操作を収めるために本文や設問を縮小しない。

### 4.3 共通コンテンツ幅

- モバイルの左右余白は16pxを基準とする
- 320pxでも横スクロールを発生させない
- 広い画面では本文を読みやすい最大幅に制限し、中央配置する
- ヘッダーと本文は同じ左右基準線を使う
- カード内部は本文の基準線からさらに適切な内側余白を取る

## 5. 共通ヘッダー

`app-header`を全画面で共有し、画面名ではなくアプリの識別と必要なナビゲーションだけを担わせる。

### 5.1 左側

- 30px程度の小さなアプリアイコン
- `Big Five 自己理解チェック`
- `BIG FIVE SELF UNDERSTANDING`

狭幅ではアプリ名を必要以上に大きくせず、英字副題との二段で収める。アプリ名を画面主見出しのように扱わない。

### 5.2 右側

右側は、その画面で意味のある操作があるときだけ表示する。

| 画面 | 右側の表示 |
|---|---|
| 開始 | なし |
| 回答・20問完答後の分岐 | `中断してトップへ` |
| 履歴 | `トップ画面へ` |
| 20問結果 | なし。既存の結果下部操作を維持 |
| 50問結果 | なし。既存の結果下部操作を維持 |
| 比較 | `履歴へ戻る` |

`はじめる`、`履歴`のような現在地ラベルは表示しない。操作はボタンまたはリンクとして認識でき、キーボードフォーカスを確認できる見た目にする。

`中断してトップへ`は320pxでも途中改行しない。必要な幅はアプリ名側の文字サイズ、要素間隔、ヘッダー内余白で確保し、操作文言を省略しない。

### 5.3 挙動

- 回答中の中断は現在のProgressRecord保持を維持する
- 履歴からの`トップ画面へ`は`#/start`へ移動する
- 結果や比較の戻り先は現在の保存状態と画面契約を維持する
- sticky表示を使う画面ではsafe areaを含め、本文の先頭を覆わない

## 6. 共通画面見出し

ヘッダー直下に、同じ役割を持つ二段の見出し領域を置く。

1. 緑の英字見出しまたは進捗
2. 黒に近い主見出しまたは設問

`.screen-heading`相当の共通構造で、次を統一する。

- ヘッダー下から英字見出しまでの余白
- 英字見出しの高さと行間
- 英字見出しから主見出しまでの間隔
- 主見出しの開始位置
- 見出し下から最初の本文または選択肢までの間隔

`HISTORY`と`1 / 20問`、`診断結果の履歴`と回答中の設問は、それぞれ同じ縦位置から始める。長い設問は開始位置を変えず、下方向へ自然に伸ばす。

開始、履歴、回答、20問完答後の分岐、結果、比較で同じ規則を使う。ただし、同じ開始位置にそろえることと、全画面を同じ文字サイズにすることは区別する。回答の設問は20〜22pxの既存基準を維持する。

## 7. 画面別設計

### 7.1 S-001 開始

表示順は次のとおりとする。

1. 共通ヘッダー
2. `SELF CHECK`
3. `自分のことを知る`
4. Big FiveとIPIPの説明
5. 診断内容を示すカード
6. 主操作
7. 十分な余白または区切り
8. `診断結果の履歴を見る`
9. 版情報へ到達できる`この診断について`

診断内容のカードは、20問が簡易プレビュー、50問が詳細結果であることを利用者の言葉で伝える。開発状況を主文にしない。

`診断を始める`を明確な主ボタンとする。`診断結果の履歴を見る`は主ボタンと横並びまたは直結させず、別の目的を持つ補助導線として間隔または区切りを設ける。

互換途中回答がある場合の再開、新規開始、置換確認は現在の状態別表示を維持する。

### 7.2 S-002 回答

- 共通ヘッダー右側に`中断してトップへ`
- 緑の進捗を`1 / 20問`または`21 / 50問`形式で表示
- その下の共通開始位置から設問を表示
- 回答選択肢5件を設問の下へ十分な間隔で並べる
- `前へ`を維持する
- `その他の操作`と、その配下の`回答を破棄`を維持する

`前へ`などが以前のデザイン確認用モックアップで省略されていたことを、実装上の削除根拠にしない。

20問完答後の選択画面も同じヘッダーと見出し規則を使い、`簡易プレビューを見る`と`結果を見ず50問へ進む`の意味や非開示契約を変えない。

### 7.3 S-006 履歴

- 共通ヘッダー右側へ`トップ画面へ`を移動する
- 本文先頭を`HISTORY`、`診断結果の履歴`の二段にする
- 本文中の`開始画面へ戻る`は重複するため外す
- 説明文の後に`履歴削除`を明示的なボタンとして置く
- 現在の`…`は外す

`履歴削除`は既存の履歴管理ダイアログを開く。個別削除、全削除、版情報、確認、Escape、フォーカス復帰、fallbackの契約は変更しない。

結果カードは猫、称号、日時、20問／50問、`結果を見る`を維持する。比較モードと画面下部の固定比較操作も維持し、safe areaと重ならないようにする。

### 7.4 S-003・S-004 結果

- 共通ヘッダーを適用する
- 20問の英字見出しは`PREVIEW RESULT`、50問は`DETAIL RESULT`とする
- `20問簡易プレビュー`または`50問詳細結果`を主見出しとして共通位置から開始する
- 称号、猫、副題、称号理由、因子結果、振り返り、方法説明、各操作の内容と順序は既存の承認済み方針を維持する

今回の変更で結果文を短縮、再生成、要約しない。長い結果画面では共通ヘッダーと見出しが主内容を圧迫しない大きさにする。

### 7.5 S-007 比較

- 共通ヘッダー右側に`履歴へ戻る`
- `COMPARISON`と`診断結果の比較`を共通見出し位置に置く
- 古い結果、新しい結果、変化量、非互換理由の現在の意味を維持する

### 7.6 空・失敗状態

空履歴、保存失敗、画像失敗、Canvas失敗、直接URL不正などでも、共通ヘッダーと画面見出しの位置を変えない。通知を見出しより上へ割り込ませず、対象操作または主内容の近くで読み上げ可能に表示する。

## 8. コンポーネントとCSSの境界

主な変更対象は次を想定する。

- `app/js/presentation/app-header.js`
- `app/js/presentation/start-screen.js`
- `app/js/presentation/questionnaire-screen.js`
- `app/js/presentation/history-screen.js`
- `app/js/presentation/result-screen.js`
- 比較画面を描画するpresentationモジュール
- `app/css/styles.css`
- 対応するpresentationテスト

共通化する責務:

- ヘッダーのブランド表示と任意の右操作
- 画面見出しの二段構造
- 文字、余白、最大幅、カード、ボタンの基本トークン

各画面に残す責務:

- 画面固有の文言
- 画面固有の操作と状態
- 結果、履歴、比較のデータ描画
- 保存失敗などの利用者向け通知

画面固有セレクタを一括置換して結果や回答の文字階層を壊さない。共通トークンを導入したうえで、設問、結果hero、履歴カードなど必要なスコープを維持する。

## 9. アクセシビリティ

- すべての操作は意味のある文言を持つ
- 見た目だけの英字見出しで画面名を代替せず、主見出しを適切なheadingとして公開する
- フォーカスリングを消さない
- 文字色、境界線、ボタン色は既存のコントラスト要件を維持する
- 320px、200%文字拡大、キーボード操作で本文と操作を失わない
- stickyヘッダーと固定比較バーはsafe areaを考慮する
- `履歴削除`はダイアログを開く操作であり、押した直後に削除しない
- `中断してトップへ`は回答破棄と誤認させず、現在の保存・通知契約を維持する

## 10. 検証

### 10.1 自動テスト

- 共通ヘッダーに新しいアプリ名と英字副題が表示される
- 開始画面に`自分のことを知る`と承認済み説明文が表示される
- 開始画面から`5つの傾向`、`はじめる`、`正式版MVPを準備中です`が外れる
- 履歴の`トップ画面へ`がヘッダー操作となる
- 履歴の`履歴削除`が既存管理ダイアログを1回だけ開く
- 回答の`前へ`、`その他の操作`、`回答を破棄`が維持される
- 20問分岐、結果、履歴、比較の既存イベント委譲が変わらない
- ResultSnapshot、ProgressRecord、採点、称号、結果文のテストが無変更で成功する
- 静的検証が成功する

### 10.2 ブラウザ確認

320px、360px、960pxで、開始、回答、20問分岐、20問結果、50問結果、履歴、比較を確認する。

- 同じ役割の英字見出しが同じ縦位置から始まる
- 同じ役割の主見出しまたは設問が同じ縦位置から始まる
- ヘッダーのアプリ名が過度に大きくない
- `中断してトップへ`が改行されない
- 主操作と履歴導線が近接しすぎない
- 履歴の主見出しが過度に大きくない
- `履歴削除`が明示され、既存管理操作へ到達できる
- 回答の`前へ`と二次操作が利用できる
- 結果本文、称号、猫、全結果文へ到達できる
- 横スクロール、文字切れ、固定要素による隠れがない

キーボードでは、ヘッダー操作、回答、二次操作、履歴管理、結果開閉、比較を順に操作し、フォーカスの見失いがないことを確認する。

## 11. 文書同期

実装時に、実際に採用した共通ヘッダー契約、表示名称、見出し構造、履歴管理導線を次へ反映する。

- `docs/screens.md`
- `docs/tasks.md`
- 必要に応じて`基本設計サマリ.md`

データ、処理、保存契約を変更しないため、`docs/data-model.md`と`docs/processing-design.md`は原則変更しない。実装中に契約変更が必要と判明した場合は、本設計の範囲拡大として扱い、先に設計を更新する。
